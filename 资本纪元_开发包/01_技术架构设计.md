# 资本纪元：交易所大亨

## 01. 技术架构设计

本文档目标：

- 明确 Flutter + Rust + PostgreSQL 的整体技术方案
- 限定 MVP 阶段的边界
- 让前后端可以同时开工

---

## 一、总体架构

整体采用三层结构：

1. `Flutter 客户端层`
2. `Rust 业务服务层`
3. `PostgreSQL 数据存储层`

在 MVP 阶段，建议先做成一个单体后端服务，再逐步拆分模块。

### 架构原则

- 客户端只负责展示、交互、轻计算
- 所有交易、资产、信用、风控逻辑统一放在后端
- 数据库只做持久化和查询，不承载业务判断
- 实时性优先保证“足够及时”，不一开始追求高频撮合系统

---

## 二、平台目标

## 2.1 Android

定位：

- 主力平台
- 优先保证完整交互体验
- 优先适配中等尺寸手机

## 2.2 Web

定位：

- 辅助平台
- 偏管理和查看
- 适合看行情、看榜单、做中轻度操作

### 结论

MVP 阶段建议：

- 以 Android 交互为主设计
- Web 保持同一业务逻辑
- Web 在布局上做更宽屏的信息分区

---

## 三、Flutter 客户端架构

## 3.1 技术建议

建议依赖：

- 路由：`go_router`
- 状态管理：`riverpod`
- 网络：`dio`
- 数据模型：`freezed`、`json_serializable`
- 本地缓存：`shared_preferences` 或 `hive`

## 3.2 分层结构

建议采用：

- `presentation`：页面、组件、交互
- `application`：状态、控制器、用例编排
- `domain`：实体、枚举、核心规则抽象
- `infrastructure`：接口请求、DTO、存储

### 推荐目录

```text
lib/
  app/
  core/
  features/
    auth/
    home/
    market/
    stock/
    ipo/
    bank/
    portfolio/
    news/
    credit/
  shared/
```

## 3.3 客户端状态分层

建议把状态分为三类：

### UI 状态

- tab 切换
- loading
- 弹窗
- 表单输入

### 页面业务状态

- 首页资产摘要
- 股票详情
- IPO详情
- 银行详情
- 新闻列表

### 会话状态

- 当前登录用户
- token
- 用户权限
- 风险提示已读状态

## 四、Rust 后端架构

## 4.1 技术选型建议

建议：

- Web 框架：`axum`
- 异步运行时：`tokio`
- 数据库访问：`sqlx`
- 序列化：`serde`
- 配置：`config` 或 `figment`
- 日志：`tracing`
- 错误处理：`thiserror`、`anyhow`
- ID：`uuid`
- 时间：`chrono`

## 4.2 服务形态

MVP 阶段采用：

- 一个后端仓库
- 一个主 API 服务
- 一个后台定时任务模块

不要一开始就拆微服务。

## 4.3 后端推荐分层

建议采用：

- `router`：路由定义
- `handler`：HTTP 入参出参
- `service`：业务编排
- `repo`：数据库读写
- `model`：数据库模型
- `domain`：核心规则对象
- `job`：定时任务

### 推荐目录

```text
src/
  main.rs
  app/
  config/
  router/
  handlers/
  services/
  repos/
  models/
  domains/
  jobs/
  utils/
```

## 五、数据库架构

## 5.1 PostgreSQL 的职责

负责存储：

- 用户
- 钱包与资产
- 股票与IPO
- 订单与成交
- 银行与贷款
- 新闻与公告
- 信用记录

## 5.2 数据设计原则

- 主键统一使用 `uuid`
- 金额字段统一使用 `numeric`
- 时间统一使用 `timestamptz`
- 状态字段统一使用 `varchar` 或枚举
- 重要对象使用 `created_at`、`updated_at`

## 5.3 不建议首版使用的东西

MVP 阶段不建议一上来就引入：

- 分库分表
- 事件溯源
- CQRS
- 独立消息队列

先保证：

- 表结构清晰
- 查询路径稳定
- 事务边界明确

## 六、实时与非实时策略

这类游戏存在“看起来要很实时”的错觉，但 MVP 可以先分层处理。

## 6.1 必须近实时的内容

- 股票最新价
- 自选列表刷新
- 首页资产摘要
- IPO状态变化

## 6.2 可以准实时的内容

- 新闻快讯
- 银行评级
- 信用变化
- 分红结算

## 6.3 技术建议

MVP 阶段建议先这样做：

- 默认接口轮询
- 对关键行情页后续补 WebSocket

优先级：

1. REST API 打通
2. 行情轮询
3. 再加 WebSocket 推送

---

## 七、事务与一致性原则

## 7.1 必须事务包裹的操作

- 下单与冻结资金
- 撮合与成交落账
- IPO申购与冻结
- 配售与退款
- 贷款发放与负债创建
- 还款与信用更新

## 7.2 一致性原则

优先保证：

- 账户资产正确
- 持仓数量正确
- 订单状态正确

允许稍后异步更新：

- 排行榜
- 推荐榜单
- 热门标签

---

## 八、认证与权限

## 8.1 认证建议

MVP 阶段建议：

- 用户注册登录
- JWT access token
- refresh token

## 8.2 权限分层

建议至少区分：

- 普通玩家
- 新手限制玩家
- 银行经营者
- 基金经营者
- 管理员

权限作用于：

- 是否可申请IPO
- 是否可开通贷款
- 是否可开设银行
- 是否可访问后台管理功能

---

## 九、后台任务系统

除了 HTTP API，还必须有后台任务。

## 9.1 建议任务

- IPO审核任务
- IPO配售任务
- 每日收盘结算任务
- 周期信用刷新任务
- 银行评级刷新任务
- 分红发放任务
- 新闻生成任务

## 9.2 技术建议

MVP 阶段不要急着引外部调度系统，先采用：

- 应用内定时任务
- 明确幂等控制
- 后续再迁移到独立任务系统

## 十、MVP 技术边界

## 10.1 建议首版必须完成

- 账户与资产
- 股票详情和下单
- 基础撮合
- 系统基金
- IPO展示与申购

## 10.2 建议第二版再做

- 玩家银行完整经营
- 复杂监管事件
- 高级期货
- 舆情系统
- WebSocket 全面实时化

## 十一、仓库组织建议

你可以选择单仓方式。

### 建议结构

```text
project/
  mobile_web_app/        # Flutter
  backend_api/           # Rust
  docs/                  # 策划和开发文档
  scripts/               # 本地开发脚本
```

如果你打算自己独立开发，这是最省心的结构。

---

## 十二、开发顺序建议

先做：

1. PostgreSQL 表
2. Rust API 骨架
3. Flutter 登录后骨架
4. 首页 + 股票页 + 资产页
5. 下单和持仓更新

再做：

1. IPO
2. 新闻
3. 信用
4. 银行基础版

---

## 十三、结论

这套技术架构的核心思路是：

- Flutter 负责跨 Android / Web 的统一客户端
- Rust 负责规则集中与高可靠业务处理
- PostgreSQL 负责主业务存储
- 首版先做单体、低复杂度实时、强事务链路

这样能在不把系统做散的前提下，尽快进入可玩版本。
